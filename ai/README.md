# AstroVitals Overarching AI (`Qwen3-8B` via Ollama)

This directory contains the local LLM configuration and fine-tuning scripts for the onboard crew health-data triage assistant:

- [`Modelfile`](./Modelfile) — Ollama Modelfile wrapping `qwen3:8b` with strict non-diagnostic guardrails, tool-bound action plans, workout modification guidance, and Flight Surgeon escalation logic.
- [`train_unsloth.py`](./train_unsloth.py) — Google Colab QLoRA fine-tuning script (`unsloth/Qwen3-8B`) using synthetic training scenarios generated by [`../astrovitals_ai_triage_code`](../astrovitals_ai_triage_code).
- **Backend Route:** [`../apps/server/src/routes/ai.ts`](../apps/server/src/routes/ai.ts) (`POST /api/ai/triage`) automatically queries Ollama (`http://localhost:11434/api/chat`) when online, and seamlessly falls back to the deterministic onboard rule engine while the model is offline or being trained.

## Quick Start with Ollama

```bash
# 1. Pull Qwen3-8B and create the custom model
ollama pull qwen3:8b
ollama create astrovitals-triage -f ai/Modelfile

# 2. The Express server automatically calls astrovitals-triage (or qwen3:8b) on POST /api/ai/triage
```

## Fine-tuning on a Mac (`ai/training/`)

A LoRA fine-tune of Qwen3-8B that runs on Apple silicon with [MLX](https://github.com/ml-explore/mlx-lm). The model is taught the rule engine's own answers, so it learns to reproduce the rules; it cannot become more accurate than they are.

| File | What it is |
|---|---|
| `make_dataset.mts` | Generates the training and validation cases and labels them with the rule engine |
| `heldout_cases.mts` | The held-out test set: boundary cases written by hand from the cited thresholds, never trained on |
| `system_prompt.txt` | The prompt the fine-tuned model is trained and served with |
| `lora_config.yaml` | Training settings |
| `evaluate.py` | Scores a model on the held-out and validation sets |
| `README-PC.md` | The same fine-tune on a PC with an NVIDIA GPU, through to an Ollama model: start there on the RTX 5090 |
| `train_cuda.py`, `merge_adapter.py`, `requirements-pc.txt` | The PC route's training script, merge step and Python packages |

```bash
# from the repository root: write ai/training/data/ (also checks the rules against the held-out set)
npx tsx ai/training/make_dataset.mts

# from ai/training: one-time setup, then train (about 75 minutes on an M-series laptop with 24 GB)
uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python mlx-lm huggingface_hub
.venv/bin/python -c "from huggingface_hub import snapshot_download; snapshot_download('mlx-community/Qwen3-8B-4bit', local_dir='base/Qwen3-8B-4bit')"
.venv/bin/python -m mlx_lm lora -c lora_config.yaml

# score it
.venv/bin/python evaluate.py mlx --adapter adapters/v2 --name tuned
```

**The 500-case test.** `make_dataset.mts` also writes `data/test500.jsonl`: 500 more random cases labelled by the rule engine, none sharing its readings with a training, validation or held-out case. It prints the file's hash (the same on every machine) and how many cases exercise each escalation rule; random cases contain few of the rare rules, so read the score beside that table. From `ai/training`:

```bash
.venv/bin/python evaluate.py mlx --adapter adapters/v2 --name tuned-test500 --test-file data/test500.jsonl                    # Mac
.venv\Scripts\python evaluate.py ollama --model astrovitals-triage-ft-v2 --name ft-v2-test500 --test-file data/test500.jsonl  # PC
```

The data, the downloaded base model, the adapters and the run logs are not committed. If the rules in `apps/server/src/routes/ai.ts` change, regenerate the data and train again.

## 1. Architecture & Clinical Design Principles

AstroVitals integrates continuous wearable vitals, daily ocular ultrasound, and pupillometry (eye dilation) into an evidence-based clinical triage engine designed for deep-space transit (`0g`), lunar (`1/6g`), and Martian (`3/8g`) missions:

1. **Personal Earth Preflight Baselines (No Synthetic Offsets):**  
   Every crew member is compared strictly against their own personal Earth preflight medians (`preflight_hr_median`, `preflight_temp_median`, `preflight_onsd_mm`) rather than generic population averages or synthetic radiation/gravity vital-sign formulas.
2. **Pre-Escalation Data Quality & Artifact Guardrails:**  
   Clinical escalation to a Flight Surgeon is automatically suppressed (`ARTIFACT_BLOCKED`) whenever hardware acquisition quality is unverified:
   - `vitals.sensor_verified === false` (loose wearable strap / motion artifact)
   - `daily_ultrasound.probe_contact_verified === false` (unverified ocular acoustic window)
   - `pupillometry.lighting_lux_verified === false` (uncalibrated ambient cabin lighting)
3. **Non-Deterministic Environmental Context:**  
   Mission location (`earth_preflight`, `deep_space_transit`, `lunar_surface`, `mars_surface`) and space weather (`quiet` vs. `storm` / Kp 7 / SEP) are logged as contextual differential factors alongside crew dosimetry—never used to fabricate deterministic BPM or SpO₂ shifts.

## 3. Neuro-Ocular & Cardiopulmonary Triage Rules

When all active channels report verified acquisition quality, `evaluateDeterministicTriage()` classifies crew status into `NOMINAL`, `MONITOR_AND_RETEST`, or `FLIGHT_SURGEON_ESCALATION`:

| Modality | Parameters Tracked | Mild Drift (`MONITOR_AND_RETEST`) | Verified Red Flag (`FLIGHT_SURGEON_ESCALATION`) |
| :--- | :--- | :--- | :--- |
| **Wearable Vitals** | `hr_bpm`, `spo2_pct`, `temp_c`, `sleep_hours` | `hr_delta_bpm >= +12` vs. personal preflight median | `hr_delta_bpm >= +35`, `spo2_pct <= 91%`, or `temp_c >= 38.0 °C` |
| **Daily Ocular Ultrasound** | `onsd_mm`, `ijv_flow_status` | `onsd_delta_mm >= +0.4 mm` or `mild_stasis` | `onsd_mm >= 5.5 mm`, `onsd_delta_mm >= +0.8 mm`, or `stagnant_retrograde` IJV flow |
| **Pupillometry (Eye Dilation)** | `left_pupil_mm`, `right_pupil_mm`, `plr_constriction_pct` | `plr_constriction_pct < 20%` (sluggish light reflex) | `anisocoria_mm >= 1.0 mm` (`|L - R|`) or `plr_constriction_pct < 15%` |

## 4. Fitbit Web API Payload Mapping

Both `ai/triage_route.ts` and the **Import Fitbit / JSON** modal in `ai/astrovitals_tracker.html` accept raw Fitbit Web API responses and map them directly into `TriageRequestSchema`:

| Fitbit Web API Endpoint | Fitbit JSON Path | AstroVitals Target Field |
| :--- | :--- | :--- |
| `GET /1/user/-/activities/heart/date/today/1d/1min.json` | `activities-heart-intraday.dataset[last].value` | `vitals.hr_bpm` |
| `GET /1/user/-/activities/heart/date/today/1d/1min.json` | `activities-heart[0].value.restingHeartRate` | `vitals.preflight_hr_median` |
| `GET /1/user/-/spo2/date/today.json` | `spo2.value.avg` | `vitals.spo2_pct` |
| `GET /1.2/user/-/sleep/date/today.json` | `sleep[0].summary.totalMinutesAsleep / 60` | `vitals.sleep_hours` |
